# Saree Store: product and technical spec (v1)

## 1. Goal and scope

A mobile-first catalogue where shoppers discover sarees and signal interest, and an admin portal where the business manages stock, reservations, and sees what people want.

**In scope (v1)**
- Public storefront: browse, filter, search, detail page, wishlist, share, WhatsApp "I'm interested", reservation request.
- Admin portal: products, images, taxonomy, sale pricing, reservations, in-store view, mark sold, analytics, settings.
- REST API shared by both, designed so a mobile app can reuse it.

**Out of scope (v1), but must not be blocked by the design**
- Payment gateway, delivery, order tracking, invoices.
- Customer accounts and login.
- Discount rules engine, coupons.
- WhatsApp Business API automation.
- Native mobile app, multiple languages.

## 2. Assumptions to confirm before coding

| # | Assumption | If wrong |
|---|---|---|
| A1 | Each saree is a unique piece (quantity 1). | Add stock quantities; §5 and §6 change. |
| A2 | A reservation is a request. It holds the saree only after an admin confirms. | Instant holds need OTP verification. |
| A3 | Backend is Spring Boot + PostgreSQL. | Rest of the spec still applies. |
| A4 | English only, prices in INR, one physical store, one WhatsApp number. | Add i18n or multi-store fields. |
| A5 | Sold sarees stay visible with a "Sold" badge for 7 days, then drop out of listings. Their links keep working. | Change the `sold_visible_days` setting. |

## 3. Users and key flows

**Shopper (no login)**
1. Opens the site or a shared link, browses and filters.
2. Hearts sarees into a wishlist kept on the device.
3. Shares a saree link (WhatsApp shows image, name, price).
4. Taps "I'm interested on WhatsApp": WhatsApp opens with a prefilled message naming the saree code and link.
5. Or taps "Reserve": enters name and phone, gets a reference, sees status on "My reservations".

**Admin (login)**
1. Adds a saree with photos, details, price; publishes it.
2. Sees new reservation requests, calls or messages the customer, then confirms, cancels, or completes.
3. In the shop, opens the in-store view to see what is available right now, and marks a saree sold or reserved for a walk-in customer.
4. Checks analytics: most viewed, most wishlisted, most asked about, what is not moving.

## 4. Architecture

```
Shopper ──> Next.js storefront ──┐
Admin ────> Vite React admin ────┼──> Spring Boot API ──> PostgreSQL
                                 │            └──> S3-compatible storage (Cloudflare R2) ──> CDN
Future mobile app ───────────────┘
```

- **Monorepo** (pnpm workspace): `apps/storefront`, `apps/admin`, `packages/ui`, `packages/api-client`, `packages/config`, plus `backend/` (Maven, outside the pnpm workspace).
- **Storefront:** Next.js App Router, server-rendered for SEO and link previews.
- **Admin:** Vite + React SPA. No SEO needs.
- **API:** versioned under `/api/v1`. OpenAPI generated by the backend; TypeScript types generated from it into `packages/api-client`.
- **Images:** uploaded straight from the admin browser to object storage with a presigned URL; served through a CDN domain.
- **Local dev:** Docker Compose runs Postgres and MinIO (S3-compatible).
- **Domains (target):** `www.<domain>` storefront, `admin.<domain>` admin, `api.<domain>` API, `img.<domain>` images.

## 5. Domain rules

### 5.1 Product

Two independent fields:

- `visibility`: `DRAFT` → `PUBLISHED` → `ARCHIVED` (admin can move between them).
- `availability`: `AVAILABLE`, `RESERVED`, `SOLD`.

Rules:
- Publishing requires: name, code, category, MRP, and at least one image with alt text.
- `code` (for example `SR-0142`) is what staff and customers quote on WhatsApp. Auto-generated from a sequence, editable until first publish, then immutable. Unique.
- `slug` is generated from name + code, unique, immutable after first publish.
- Never hard-delete a product that has reservations or events. Archive instead.
- Public API returns only `PUBLISHED` products. A `SOLD` product leaves listings after `sold_visible_days`, but its detail URL still returns 200 with a "Sold" state and similar sarees. `DRAFT` and `ARCHIVED` return 404.

### 5.2 Pricing

- `mrp_paise` is required. `sale_price_paise`, `sale_label`, `sale_starts_at`, `sale_ends_at` are optional.
- A sale is active when `sale_price_paise` is set, is lower than MRP, and now is inside the window (open-ended if a bound is null).
- `effectivePricePaise` and `discountPercent` are computed by the backend and returned in DTOs. Frontends never compute them.

### 5.3 Reservation state machine

Statuses: `PENDING`, `CONFIRMED`, `COMPLETED`, `CANCELLED`, `EXPIRED`.

| From | To | Who | Effect on product |
|---|---|---|---|
| (none) | `PENDING` | Shopper | None. Product stays `AVAILABLE`. |
| (none) | `CONFIRMED` | Admin (manual entry for WhatsApp, phone, walk-in) | `AVAILABLE` → `RESERVED` |
| `PENDING` | `CONFIRMED` | Admin | `AVAILABLE` → `RESERVED`; sets `hold_expires_at` |
| `PENDING` | `CANCELLED` | Admin or shopper | None |
| `PENDING` | `EXPIRED` | Job, after `pending_expiry_hours` | None |
| `CONFIRMED` | `COMPLETED` | Admin | `RESERVED` → `SOLD`; records sale |
| `CONFIRMED` | `CANCELLED` | Admin or shopper | `RESERVED` → `AVAILABLE` |
| `CONFIRMED` | `EXPIRED` | Job, at `hold_expires_at` | `RESERVED` → `AVAILABLE` |

More rules:
- A shopper can request only when the product is `PUBLISHED` and `AVAILABLE`. When it is `RESERVED`, the storefront shows "Reserved" and offers the WhatsApp button only.
- Several `PENDING` requests can exist for one product (a waitlist). Only one `CONFIRMED` reservation can exist per product. Enforce with a partial unique index and by locking the product row (`SELECT ... FOR UPDATE`) in every transition.
- Admin can extend a `CONFIRMED` hold (new `hold_expires_at`).
- When a product becomes `SOLD` by any path, all its `PENDING` reservations become `CANCELLED` with reason `PRODUCT_SOLD`.
- Admin "mark sold" directly (walk-in or WhatsApp sale) is allowed only from `AVAILABLE`. If the product is `RESERVED`, the admin must complete or cancel that reservation first.
- Admin "undo sold" returns the product to `AVAILABLE` and is audit-logged.
- Invalid transitions return 409 with a stable error code.
- Every transition writes an audit log row.

Anti-abuse (there is no login or payment):
- One active (`PENDING` or `CONFIRMED`) reservation per phone per product. A repeat request returns the existing one.
- At most `max_active_reservations_per_phone` (default 3) active reservations per phone.
- Rate limit by IP (§11). Hidden honeypot field in the form.
- Phone numbers are normalised to E.164 (default region IN) and validated.

### 5.4 Expiry job

A scheduled job runs every 5 minutes and expires overdue `PENDING` and `CONFIRMED` reservations through the same state machine service. It must be idempotent. v1 runs a single backend instance; add a distributed lock before scaling out.

## 6. Data model (PostgreSQL)

All tables have `id uuid` primary key (except `event`), `created_at`, and `updated_at` as `timestamptz`. Money is `bigint` paise.

**admin_user**: `email` (unique, lowercased), `password_hash`, `name`, `role` (`OWNER`, `STAFF`), `is_active`, `last_login_at`.

**refresh_token**: `admin_user_id` FK, `token_hash` (unique), `expires_at`, `revoked_at`, `user_agent`.

**term** (admin-managed filter values): `type` (`CATEGORY`, `FABRIC`, `COLOUR`, `OCCASION`), `name`, `slug`, `sort_order`, `is_active`, `colour_hex` (only for `COLOUR`). Unique on (`type`, `slug`).

**product**
- `code` (unique), `slug` (unique), `name`, `description`
- `category_id` FK term (required to publish), `fabric_id` FK term (optional)
- `mrp_paise`, `sale_price_paise`, `sale_label`, `sale_starts_at`, `sale_ends_at`
- `length_meters numeric(4,2)`, `has_blouse_piece boolean`, `care_instructions`
- `visibility`, `availability`, `is_featured`
- `published_at`, `sold_at`, `sold_price_paise`, `sold_channel` (`ONLINE_RESERVATION`, `WHATSAPP`, `WALK_IN`, `OTHER`)
- `internal_notes` (never public), `version` (optimistic lock)
- Indexes: (`visibility`, `availability`, `published_at desc`), `category_id`, `mrp_paise`; trigram or full-text index on `name` + `code` for search.

**product_term**: `product_id`, `term_id` (colours and occasions; many-to-many). Primary key on both.

**product_image**: `product_id` FK, `storage_key`, `width`, `height`, `bytes`, `content_type`, `alt_text`, `sort_order`, `is_primary`. One primary image per product (partial unique index).

**reservation**
- `reference` (unique, 6 characters, human-friendly, no ambiguous letters)
- `public_token uuid` (unique, unguessable; lets the shopper view or cancel without login)
- `product_id` FK, `customer_name`, `customer_phone` (E.164), `customer_note`
- `status`, `source` (`ONLINE`, `WHATSAPP`, `PHONE`, `WALK_IN`)
- `hold_expires_at`, `pending_expires_at`
- `confirmed_at`, `completed_at`, `cancelled_at`, `cancel_reason`, `cancelled_by` (`ADMIN`, `CUSTOMER`, `SYSTEM`)
- `handled_by_admin_id` FK, `admin_notes`
- Partial unique index on `product_id` where `status = 'CONFIRMED'`.
- Partial unique index on (`product_id`, `customer_phone`) where `status in ('PENDING','CONFIRMED')`.
- Indexes: (`status`, `created_at desc`), `customer_phone`.

**event** (analytics, append-only): `id bigserial`, `type`, `product_id` (nullable), `visitor_id uuid`, `occurred_at`, `received_at`, `path`, `referrer_host`, `utm_source`, `device` (`MOBILE`, `TABLET`, `DESKTOP`). Indexes: (`product_id`, `occurred_at`), (`type`, `occurred_at`). No IP addresses stored.

**store_settings** (single row): `store_name`, `whatsapp_number` (E.164), `contact_phone`, `address`, `hold_hours` (default 48), `pending_expiry_hours` (default 72), `sold_visible_days` (default 7), `max_active_reservations_per_phone` (default 3).

**audit_log**: `admin_user_id` (nullable for system), `action`, `entity_type`, `entity_id`, `before jsonb`, `after jsonb`, `created_at`.

## 7. API

Base path `/api/v1`. JSON, camelCase. Timestamps ISO 8601 UTC.

### 7.1 Conventions

- **Errors:** RFC 9457 Problem Details plus `code` (stable, upper snake case) and, for validation, `errors: [{field, message}]`.
  Codes include: `VALIDATION_FAILED`, `NOT_FOUND`, `UNAUTHENTICATED`, `FORBIDDEN`, `RATE_LIMITED`, `PRODUCT_NOT_AVAILABLE`, `PRODUCT_NOT_PUBLISHABLE`, `INVALID_TRANSITION`, `RESERVATION_LIMIT_REACHED`, `CONFLICT`.
- **Pagination:** `?page=0&size=24` (max size 60). Response `{items, page, size, totalItems, totalPages}`.
- **Public DTOs never contain:** phone numbers, internal notes, reservation details, analytics counts, draft or archived products.

### 7.2 Public endpoints (no auth)

| Method | Path | Notes |
|---|---|---|
| GET | `/store` | Store name, WhatsApp number, contact details |
| GET | `/taxonomy` | Active terms grouped by type |
| GET | `/products` | Filters: `category`, `fabric`, `colour`, `occasion` (slugs, repeatable), `minPrice`, `maxPrice`, `onSale`, `q`. Sort: `newest` (default), `priceAsc`, `priceDesc`, `popular`. Paginated |
| GET | `/products/{slug}` | Full detail |
| GET | `/products/{slug}/similar` | Up to 8, same category, nearest price, available first |
| POST | `/products/lookup` | Body `{ids: []}`, max 50. Hydrates the wishlist; skips unpublished ids |
| GET | `/products/sitemap` | Slugs and `updatedAt` for the sitemap |
| POST | `/reservations` | Body `{productId, name, phone, note?}`. Returns `{reference, publicToken, status, pendingExpiresAt, product}` |
| GET | `/reservations/{publicToken}` | Status view. No phone echoed back |
| POST | `/reservations/{publicToken}/cancel` | Shopper cancels a `PENDING` or `CONFIRMED` reservation |
| POST | `/events` | Body `{visitorId, events: [{type, productId?, occurredAt, path?, referrer?, utmSource?}]}`, max 20. Returns 202 |

Product summary (list) fields: `id`, `code`, `slug`, `name`, `category`, `mrpPaise`, `effectivePricePaise`, `discountPercent`, `saleLabel`, `availability`, `primaryImage {url, width, height, alt}`.
Product detail adds: `description`, `fabric`, `colours`, `occasions`, `images[]`, `lengthMeters`, `hasBlousePiece`, `careInstructions`, `publishedAt`.

### 7.3 Admin endpoints (`/api/v1/admin`, Bearer token)

**Auth**
- `POST /auth/login` `{email, password}` → `{accessToken, expiresIn, user}` and sets the refresh cookie.
- `POST /auth/refresh` → new access token; rotates the refresh token.
- `POST /auth/logout` → revokes the refresh token.
- `GET /auth/me`

Access token: JWT, 15 minutes, held in memory by the admin app. Refresh token: opaque, 14 days, stored hashed, sent as an `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/api/v1/admin/auth`. The refresh endpoint also checks the `Origin` header. Reuse of a rotated refresh token revokes the whole chain.

**Products**
- `GET /products` (all visibilities; filters: `visibility`, `availability`, `category`, `q` by name or code; paginated)
- `POST /products`, `GET /products/{id}`, `PUT /products/{id}` (sends `version`)
- `POST /products/{id}/publish`, `/unpublish`, `/archive`
- `POST /products/{id}/mark-sold` `{channel, soldPricePaise?}`
- `POST /products/{id}/undo-sold`

**Images**
- `POST /products/{id}/images/upload-url` `{contentType, bytes}` → `{uploadUrl, storageKey, expiresAt}`
- `POST /products/{id}/images` `{storageKey, altText}` → backend checks the object exists, type, size, reads dimensions
- `PATCH /products/{id}/images/{imageId}` `{altText?, isPrimary?}`
- `PUT /products/{id}/images/order` `{imageIds: []}`
- `DELETE /products/{id}/images/{imageId}`
- Limits: JPEG, PNG, WebP; 8 MB each; 8 images per product.

**Taxonomy:** `GET/POST /terms`, `PUT /terms/{id}`, `DELETE /terms/{id}` (blocked if in use; deactivate instead).

**Reservations**
- `GET /reservations` (filters: `status`, `productId`, `phone`, `source`, date range; paginated; includes waitlist count per product)
- `GET /reservations/{id}`
- `POST /reservations` (manual; creates `CONFIRMED`)
- `POST /reservations/{id}/confirm` `{holdHours?}`, `/cancel` `{reason}`, `/complete` `{soldPricePaise?}`, `/extend` `{holdExpiresAt}`
- `PATCH /reservations/{id}` `{adminNotes}`
- `GET /reservations/summary` → counts by status, used for the "new requests" badge

**Analytics** (all take `from`, `to`)
- `GET /analytics/overview` → totals and a daily series for views, unique visitors, wishlist adds, WhatsApp clicks, shares, reservation requests
- `GET /analytics/products` → per-product table of the same metrics; sortable; paginated
- `GET /analytics/inventory` → counts by availability and by category, total MRP value of available stock
- `GET /analytics/sales` → sarees sold, total sold value, and average sold price, split by channel (online reservation, WhatsApp, walk-in), with a daily series. When `soldPricePaise` is omitted on mark-sold or complete, the backend stores the effective price at that moment, so every sale has a value
- `GET /analytics/insights` → "wanted but unreserved" (high interest, still available) and "not moving" (published 30+ days, low views)

**Settings:** `GET /settings`, `PUT /settings` (OWNER only).
**Users:** `GET/POST /users`, `PUT /users/{id}`, `POST /users/{id}/reset-password` (OWNER only).

## 8. Storefront (Next.js)

### 8.1 Routes

| Route | Purpose |
|---|---|
| `/` | Featured sarees, new arrivals, category tiles |
| `/sarees` | Listing with filters, sort, pagination (all in URL params) |
| `/sarees/[slug]` | Detail: gallery, price, details, badges, actions, similar sarees |
| `/wishlist` | Wishlisted sarees on this device; "Send my wishlist on WhatsApp" |
| `/reservations` | Reservations made on this device, with live status |
| `/about`, `/contact`, `/privacy` | Static pages |
| `/sitemap.xml`, `/robots.txt` | Generated |
| `/api/revalidate` | Called by the backend with a shared secret to refresh cached pages |

### 8.2 Behaviour

- **Product card:** portrait image (3:4), name, price (MRP struck through when on sale), badge (`Reserved`, `Sold`, or sale label), heart button.
- **Detail actions:** Wishlist, Share, "I'm interested on WhatsApp", Reserve. When `RESERVED`: no Reserve button. When `SOLD`: no actions except Wishlist-free "See similar".
- **Wishlist:** list of product ids in `localStorage` (small Zustand store with persist). Hydrated through `POST /products/lookup`. Items that are no longer published are dropped quietly.
- **Share:** Web Share API where available; otherwise copy link plus a WhatsApp share link.
- **WhatsApp interest:** opens `https://wa.me/<number>?text=<encoded>` with:
  `Hi, I'm interested in this saree: <name> (<code>), ₹<price>. <url>`
- **Wishlist on WhatsApp:** one message listing each saree's code, name, and link.
- **Reserve form:** name, phone, optional note, consent line linking to `/privacy`. On success: show reference, expiry of the request, and a WhatsApp button prefilled with the reference. Save `publicToken` in `localStorage`. On `PRODUCT_NOT_AVAILABLE`: explain and refresh the page state.
- **Visitor id:** random UUID in `localStorage`, used only for analytics events. No cookies.
- **Mobile navigation:** a sticky bottom bar on phones with Home, Sarees, Wishlist (with count), and Reservations.

### 8.3 SEO and link previews

- `generateMetadata` on the detail page: title, description, canonical URL, Open Graph and Twitter tags using the primary image, name, and price.
- JSON-LD `Product` with `offers` (price, INR, availability).
- Keep the Open Graph image small in file size, and test previews on a real phone in WhatsApp before launch.
- Sitemap built from `/products/sitemap`.

### 8.4 Caching

- Product and listing fetches are tagged (`products`, `product:<slug>`, `taxonomy`).
- The backend calls `/api/revalidate` after a product, image, term, or availability change commits. Fallback: time-based revalidation every 5 minutes.
- The reserve endpoint is always the source of truth for availability.

## 10. Analytics

Event types: `PRODUCT_VIEW`, `WISHLIST_ADD`, `WISHLIST_REMOVE`, `SHARE_CLICK`, `WHATSAPP_CLICK`, `RESERVE_SUBMIT`, `LIST_VIEW`.

- The storefront batches events and sends them with `navigator.sendBeacon` (or `fetch` with `keepalive`).
- The backend drops obvious bots by user agent, ignores unknown product ids, and caps events per request.
- v1 reports query the `event` table directly. Add a daily rollup table only when queries get slow.
- Raw events are kept for 180 days, then deleted by a scheduled job.
- "Unique visitors" means distinct `visitor_id`.

## 11. Security and privacy

- HTTPS everywhere. Security headers on all three apps (HSTS, `X-Content-Type-Options`, `Referrer-Policy`, a Content Security Policy).
- CORS allow-list: only the storefront and admin origins. Credentials allowed only for the admin origin.
- Passwords hashed with Argon2id or BCrypt. Minimum 10 characters.
- First admin is created at startup from `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` only when no admin exists.
- Rate limits (in-memory token buckets in v1): login 5 per 15 minutes per IP + email; `POST /reservations` 5 per hour per IP; `POST /events` 60 per minute per IP. Trust `X-Forwarded-For` only from the known proxy.
- Uploads: validate content type and size on both the presign and confirm steps; random storage keys; no public write access to the bucket.
- Customer name and phone are personal data: admin-only, masked in logs, never in URLs, never in public responses. The privacy page says what is collected and why. Check legal obligations for customer data before launch.
- Secrets only in environment variables. Dependency scanning in CI.
- Database backups: daily, with a tested restore.

## 12. Quality

- **Backend tests:** unit tests for pricing and the reservation state machine (every row of §5.3, plus invalid transitions); integration tests with Testcontainers; a concurrency test proving two simultaneous confirms on one product yield exactly one `CONFIRMED`.
- **Frontend tests:** Vitest for helpers (money, WhatsApp message builder, wishlist store) and key components.
- **End-to-end (Playwright):**
  1. Admin creates and publishes a saree; it appears on the storefront.
  2. Shopper wishlists a saree and sees it on `/wishlist`.
  3. Shopper reserves; admin confirms; storefront shows "Reserved"; admin completes; storefront shows "Sold".
  4. Hold expires; saree is available again.
- **CI (GitHub Actions):** lint, typecheck, tests, and builds for backend and frontends on every pull request. Fails if the generated API client is out of date.
- **Performance:** listing and detail pages target a mobile Lighthouse performance score of 90+. Images are responsive and lazy-loaded below the fold.
- **Accessibility:** keyboard-usable, labelled controls, colour contrast at WCAG AA.
- **Observability:** structured JSON logs with a request id; Spring Actuator health; an error tracker on all three apps; an external uptime check on the storefront and the API health endpoint.

## 15. Future scope (keep the door open)

Likely first, soon after launch:
- **New-reservation alerts:** email or WhatsApp message to the store when a request arrives, so nobody has to watch the admin inbox.
- **Home page banners:** admin-managed hero banners with start and end dates (festive offers, new collections).
- **Bulk product import:** CSV upload for product details, with images added afterwards.

Later:
- **Payments and orders:** prices are already in paise; a reservation can grow into an order. Rules to follow when this is built: order totals and discounts are computed on the server only, never trusted from the client; payment webhooks are verified by signature; stock changes and order creation happen in one database transaction; coupon usage is recorded in that same transaction.
- **Coupons and discount rules:** codes with percent or flat value, minimum order, date window, usage limits. Non-stackable by default.
- **Customer accounts:** `visitor_id` and the local wishlist can merge into an account at first login. Order history and saved addresses follow.
- **Stock quantities and variants:** replace product `availability` with counts; reservations then hold a unit.
- **Reviews** on sold sarees or the store.
- **Category hierarchy:** a parent on `term` for sub-categories.
- **Mobile app:** reuses the public API; add token auth for customers and push notifications.
- **WhatsApp Business API:** automatic confirmations and reminders.
- **Languages:** keep user-facing strings in one place per app so they can be translated later.
- **Scaling out:** more than one backend instance needs a shared store (Redis) for rate limits and a distributed lock for the expiry job.
